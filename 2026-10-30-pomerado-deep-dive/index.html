The central design: spend model reasoning while constructing an integration, retain the resulting source and contracts, then execute that code on subsequent calls. Most of the interesting engineering concerns evidence: what was actually run, what changed on the website, which inputs were exercised, and whether a failed write is safe to repeat. pomerado.ts:19 ↗ run-operation.ts:75 ↗ run-outcome.ts:618 ↗

01 / ORIENTATION

Think of it as an integration factory.

You give Pomerado a website, a task, an optional concrete input, and permission to read or write. Its minter explores the site in Chromium, writes operation modules, executes reviewed steps, and produces an integration directory. Your agent can then call that integration through a local MCP server. The saved operation still performs browser automation; removing model inference from a run does not remove the website or browser from the dependency chain. mint-host.ts:207 ↗ mcp-package.ts:44 ↗ run-operation.ts:75 ↗

The README's “website into an API” framing is easiest to understand as a typed callable capability. In this repository's local path, the concrete exposed interface is MCP over stdio, with a library and terminal interface too. This is not an automatic public REST deployment. The generated server exposes a business operation plus job helpers. mcp-server.ts:182 ↗ mcp-server.ts:315 ↗

At construction time

A model reasons about the site, writes code, gets execution feedback, answers review findings, and generalizes the demonstrated task.

Inputs: task, site, authority, example.
Output: source + schemas + evidence-backed packaging.

At execution time

The runtime loads that source, validates arguments, manages a browser session, executes the operation, and classifies the result.

Inputs: typed business arguments.
Output: structured data or a job/failure record.

“Deterministic” describes the execution plan: the saved code runs without a new model deciding each action. It is not a mathematical promise that a live website always produces the same result. Login state, inventory, page structure, timing, anti-bot systems, and generated-code mistakes still affect the outcome. That distinction is an engineering inference from the runtime's browser-dependent implementation. run-operation.ts:75 ↗ playwright-worker.ts:39 ↗

Scope of this report: the pinned open-source revision and its local host. I traced the main execution paths, examined supporting contracts and tests, and ran checks below. This is not a line-by-line audit of all 264 TypeScript source files, a security certification, or a benchmark of live model-generated integrations.

02 / THE SYSTEM MAP

One codebase, two very different paths.

The local composition root is small: createPomerado owns a scoped session and exposes mint and run. A semaphore serializes access to that session. The larger work is delegated into shared modules and host adapters. Effect supplies scoped lifetimes, typed failures, cancellation, and concurrency primitives; it is part of the backend implementation, not a frontend framework. pomerado.ts:19 ↗ session.ts:10 ↗

1 / 6

1. Reserve resources before doing work

prepareIntegration validates the deployment name, resolves the configured root, and creates the target directory exclusively. An existing name fails before the site task runs. The reserved directory is removed if the mint does not complete. This prevents a successful website action from being followed by an avoidable “name already exists” packaging failure. mcp-package.ts:44 ↗

2. Give the model a workspace and an explicit tool contract

The local host wires the minter to a workspace, a browser, an input asker, review functions, deadlines, live testing, and publication. The authoring catalog is purpose-specific: core operations, authentication, search, forms, pagination, writes, cart behavior, caller input, testing, and publication. These are working instructions with examples, loaded into the minter's context as needed. mint-host.ts:58 ↗ skills.ts:15 ↗

The model can inspect source, edit files, execute steps, ask reviewed questions, propose task updates, run live test batches, finish a build, or report that it is blocked. An execution declares a purpose such as explore, authenticate, example, test, or act. A target specifies its execution environment. Shared contracts include more environments than the local host supports; locally, the preflight admits pureFiles and liveBrowser. contracts.ts:843 ↗ mint-host.ts:58 ↗

3. Turn observations into a parameterized operation

The minter explores what the actual site offers, then writes an operation with input and output schemas. For the catalog example, discovering a category dropdown is insufficient: the generated code needs to apply the caller's category, wait for the site's response, and verify it stuck. A fixed scrape that ignores an input can return plausible data while violating the contract. The search and testing guidance explicitly targets that failure mode. skills.ts:15 ↗ live-tests.ts:38 ↗

4. Review, dispatch, and retain a receipt

The host checks syntax, purpose, target, and build state before calling the review/execution adapter. Guardian inspects the current source and trusted authority. On approval, the host dispatches the operation and retains structured evidence. Refusal is a result the minter can use to revise its proposal; it is not permission to try the same action through an unreviewed route. step-checks.ts:36 ↗ mint-execution.ts:741 ↗ session.ts:78 ↗

The loop also protects ordering. Read-only source inspection can be grouped; mutating tools execute in order. If an execution does not produce a completed receipt, later calls in that model response are withheld so the minter can reconsider with the result in view. These orchestration rules matter when one response includes both a code edit and an execution. openai.ts:145 ↗

5. Check the generalization, not just the happy-path example

A public read can design varied cases in test/cases.json, including no results, combined filters, boundary inputs, and pagination. Signed-in reads have a stricter bound: four distinct test inputs beyond the example. The local batch runner serializes cases on its browser, preserving its session; this does not establish cold-start behavior across unrelated browser profiles. live-tests.ts:38 ↗ mint-live-tests.ts:1 ↗

6. Publish the source that the evidence supports

finish_build is a structured completion operation, not just a final chat message. Publication selects the source closure, checks it for retained secrets and build-only handles, extracts the operation contract, compares evidence, and obtains a publication review. The resulting files become an artifact only after those checks accept it. Here “publication” means saving an integration; it does not mean posting it to a public registry or GitHub Pages. mint-publication.ts:235 ↗ operation-source.ts:26 ↗

04 / EFFECTS ON THE WEBSITE

A write is performed while the tool is being built.

This is the biggest behavioral surprise for a first-time user. A request to build a write integration is not a dry run: the mint performs the authorized action in its live write session. It then composes and reviews the reusable implementation without repeating the business write simply to test the final combined script. Read builds and write builds therefore need different evidence. step-checks.ts:36 ↗ write-session.ts:242 ↗ mint-publication.ts:235 ↗

ConcernRead buildWrite build
Live workExplore, run an example, exercise relevant test inputs.Explore and perform one authorized act session, potentially across multiple steps.
Generalization evidenceExample output and live test cases on the source being published.The actual act session, its commit marks, readbacks, and review of the composed source.
Retry riskRepeated reads may still consume time or hit site limits.A repeat can duplicate a real-world change. Uncertain effects require investigation.
PublicationShow that the current read source works for the claimed inputs.Show that the session and final contract agree without executing the write twice.

Write declarations identify meaningful commit steps and how the operation establishes success. Before sending a state-changing step, generated code records enteringCommit(name). After observing the site's confirmation or saved state, it can mark the result verified. The journal distinguishes nothing sent, a possible effect, and a verified effect. It is evidence about execution, not a database transaction that can roll the external website back. operation.ts:39 ↗

An outcome reviewer assesses writes after they return, fail, or lose their result. It reads retained history and execution evidence and can request a readback through the minter's ordinary reviewed path. It has no direct browser or shell tool of its own. A prior write that may have been sent cannot simply be rerun because its response was lost; matching entrypoints and source digests are tracked, and Guardian also sees prior write outcomes. outcome-review.ts:319 ↗ how-it-works.md:208 ↗

Practical consequence

“Make me an integration that submits this form” can submit the form during minting. Use a read-only task first. For later write experiments, choose a reversible action in a controlled account and give explicit authorization for that actual action.

05 / REVIEW IS PART OF THE LOOP

Guardian decides whether a proposal may execute.

Guardian is a second model session with policy, source-reading tools, and trusted context supplied by the host. The minter's own claim that an action is safe does not substitute for host authority. Reviews cover proposed executions, questions, task changes, and final publication. The reviewer is told which protections the current host actually provides. review.ts:78 ↗ session.ts:78 ↗ execution-policy.ts:40 ↗

A useful mental separation is intent before execution versus evidence after execution. Guardian decides whether to allow a proposal. The outcome reviewer decides whether an attempted write appears to have happened. Combining those into a single “the model approved it” flag would lose the distinction between an authorized action and a successful one. mint-execution.ts:741 ↗ how-it-works.md:208 ↗

Why this is more than a prompt

The host enforces structural checks independently: permitted tools, syntax validation, allowed step purposes, source snapshots, question declarations, source/handle screening, schema checks, and write-session boundaries. Publication is conditioned on the host's evidence rather than a free-form success statement. The model's policy reasoning is one layer among those mechanisms. mint-host.ts:58 ↗ step-checks.ts:36 ↗ mint-publication.ts:235 ↗

Where the trust boundary ends

The local host executes with the operating-system user's permissions. Its workspace and process groups manage files and cleanup; they do not provide filesystem or network containment. The policy explicitly tells Guardian that local modules, browser code workers, and shell commands are native execution. The default child environment is separately constructed, which limits ambient environment propagation, but that is not an OS sandbox. local-process.ts:32 ↗ local-workspace.ts:344 ↗ execution-policy.ts:40 ↗

Saved integrations receive no fresh Guardian review on each call. Manual changes to src/ or deployment metadata are not automatically reapproved. Inference: artifact provenance and local code review matter, especially if someone hands you an integration directory. A package claiming a read-only MCP hint is not sufficient evidence that arbitrary edited source cannot write. run-operation.ts:75 ↗ mcp-package.ts:44 ↗

// Illustrative adaptation of the repository's native-page example.

import { Schema } from "effect";
import { defineOperation } from "pomerado/runtime";

export default defineOperation({
  name: "read_heading",
  input: Schema.Struct({}),
  output: Schema.Struct({ heading: Schema.String })
}, async ({ kernel, sessionId }) => {
  const response = await kernel.browsers.playwright.execute(sessionId, {
    code: "return await page.locator('h1').innerText();",
    timeout_sec: 10
  });
  if (!response.success) throw new Error(String(response.error));
  return { heading: response.result };
});

07 / THE FAST PATH

A saved call executes code, not a new plan.

  1. Validate the business call. The MCP adapter canonicalizes the declared input schema, wraps it under input, and validates arguments before starting work. Write tools optionally accept an idempotency_key. mcp-server.ts:257 ↗
  2. Start or recover the job identity. The host checks the retry key when present, then runs the operation in a scoped Pomerado session. The default local MCP concurrency limit is one job; the API permits configuring a limit from 1 to 16. mcp-server.ts:315 ↗ mcp-jobs.ts:266 ↗
  3. Check preconditions before touching the site. Signed list cursors and declared file-size/type constraints are admitted before sign-in or navigation. The source is staged into a local runtime workspace. run-operation.ts:75 ↗
  4. Sign in and establish the start page. A recorded recipe is replayed when required. The operation starts at the site's root and navigates deeper itself. Served calls receive new browser contexts; a library caller can share a context within its createPomerado scope. run-operation.ts:75 ↗ pomerado.ts:19 ↗
  5. Execute and gather a journal. The operation child talks to the browser adapter, asks only declared questions, handles dialogs and file capabilities, and streams evidence about effects. Deadlines and scoped cleanup contain resource lifetime. local-operation.ts:42 ↗ local-process.ts:32 ↗
  6. Validate and classify the return. A valid read or confirmed write can return data. Failures retain information about write status and retryability. A write's result cannot be treated as an innocuous retry merely because output validation failed after the website changed. run-operation.ts:75 ↗ run-outcome.ts:618 ↗

Running a saved tool needs no model key. The browser, the website, and any required sign-in still have runtime cost and latency. The repository does not provide evidence that all websites or all workflows can be reliably converted; that remains a property to measure per integration. run-operation.ts:75 ↗

08 / CONTINUATION WITHOUT RESUBMISSION

A job ID is a handle to work already started.

ToolWhat it doesWhy it matters
mint / business toolStarts work, or finds a keyed existing write job.Do not repeatedly call this to poll a long-running action.
get_jobWaits for status, input needs, completion, or failure; wait is bounded at 30 seconds.Observation does not replay the website task.
provide_inputAnswers the current request using its request ID and declared answer format.Continues the same suspended job.
cancel_jobInterrupts the local job and waits for resource cleanup.Cannot undo a website action already dispatched.

These helpers are shared between minting and served integrations. Fast business calls may complete within the initial wait; slower calls return a job view. MCP answers are not a private channel from the user to a website: secret values sent through provide_input are visible to the MCP client and its model provider. mcp-server.ts:99 ↗ mcp-server.ts:315 ↗

Idempotency is deliberate and bounded

For a served write with an integration directory, keyed job records persist in .jobs. The store scopes the key to the tool and fingerprints its input. Reusing the key with the same request returns the original job rather than executing again; a conflicting request is not a fresh action under the same key. Finished records are retained for a day. The persisted record contains status and outcome metadata, not the full business input or output. local-job-store.ts:75 ↗ mcp-server.ts:315 ↗

This is duplicate-submission prevention within the store's scope and retention, not an exactly-once guarantee for a third-party website. Unkeyed jobs do not gain cross-restart identity. Process loss does not rewind an external transaction, and a retained completed record after restart does not reconstruct the output that was never persisted. local-job-store.ts:75 ↗ mcp-jobs.ts:266 ↗

Two different meanings of retry: a failure's retry classification describes whether the request is safe to attempt again. A reused idempotency key still answers the existing job, even if that job failed. Creating another execution of a failed keyed job needs a new key; do that only after respecting its outcome and readback requirements. how-it-works.md:227 ↗ local-job-store.ts:75 ↗

10 / CREDENTIALS, FILES, AND CONTEXT
The host mediates sensitive browser interaction.


During minting, the model discovers sign-in controls while the host's authentication path handles entry and recording. A saved auth-fill.json describes the sign-in flow; it is not a saved password store. Subsequent local calls ask for login values and any required codes or approvals. Recipe failure stops execution rather than silently proceeding signed out. artifact-files.ts:11 ↗ autofill-replay.ts:1 ↗ run-operation.ts:75 ↗


Credential entry is restricted to the site's origin and configured authentication origins, with checks on the relevant fields and submit destination. That does not prove what the page's own scripts do after receiving a value. Also, allowing a trusted authentication origin for entry is not a promise that every multi-origin SSO flow can be published by the local host. The build and recipe publication constraints are narrower. sign-in-origins.ts:1 ↗ mint-publication.ts:235 ↗


Three boundaries to keep separate
  • Provider credential: the OpenAI API key used to mint belongs in the server environment, not in generated source or client messages.
  • Website credentials: values collected for sign-in are tracked and screened within the session, and the generated artifact should retain a recipe rather than those values. session.ts:10 ↗ secrets.ts:1 ↗
  • Business output: legitimate site data returned by an operation is still data. The documentation states runtime output is returned without secret redaction, so “the runtime masks sign-in secrets” must not be generalized to “all returned business data is safe to share.” how-it-works.md:227 ↗


Files are another explicit capability. The local input interface uses file references, not raw bytes embedded in page code. The host restricts uploads to files named by the caller and collected outputs to files the run actually obtained. Defaults cap each file at 25 MiB and a run at 10 files / 50 MiB. These are runtime transfer limits, unrelated to this report's publisher. file-transfer.ts:1 ↗ files.ts:1 ↗


Operational inference: generated source and MCP manifests deserve review before sharing. The sign-in recipe is designed to omit credential values, but schemas, source, example-derived constants, and outputs can still expose site-specific or sensitive business context if treated carelessly. This report uses only public repository code and synthetic test data.





11 / THE SMALL MECHANISMS THAT MATTER
Reliability is assembled from explicit contracts.


Pagination is a protocol, not a “next” click
The runtime defines list limits, continuation shapes, site mechanisms, and refusal reasons. The default page size is 20 and maximum requested size is 50. A signed cursor binds continuation to the operation, site, and relevant input; the local artifact scope includes a digest of its source files. Tampering, changed inputs, incompatible source, or expiration can therefore be rejected before browser work. list-page.ts:18 ↗ list-cursor.ts:201 ↗ list-cursors.ts:49 ↗


The actual cursor lifetime constant is 600_000 milliseconds: ten minutes. Default local signing keys live for the process lifetime, so a server restart also invalidates cursors unless a library host explicitly supplies stable keys. One comment in run-operation.ts still says “hour”; the constant and cursor implementation are the authoritative behavior used here. list-page.ts:18 ↗ list-cursors.ts:49 ↗ run-operation.ts:75 ↗


Passing tests is evidence with qualifications
The minting live-test gate normally requires at least 70% of counted cases on the published version to pass before review. “Counted” excludes stale, inconclusive, not-run, and retired cases; no counted cases passes this numeric gate. The gate can also lift when no further cases can run within the attempt's testing allowance, leaving the publication review to judge the remaining evidence. This is not a claim of 70% production reliability or universal coverage. live-tests.ts:1363 ↗


The local host does not enable the stricter optional “hold review while any counted case fails” policy. Publication review still examines test records and claims. The system tries to retain meaningful failed-case history so deleting or relabeling a case is not, by itself, proof that the defect disappeared. live-tests.ts:1363 ↗ mint-live-tests.ts:1 ↗


Timeouts distinguish active work from waiting for the owner
The shared deadline defaults to 20 minutes of execution budget. It supports explicit suspension for trusted waits. Navigation and action waits have separate bounds; operation code is encouraged to wait for the relevant visible state rather than sleeping for an arbitrary interval. This keeps the execution budget meaningful without forcing a human to answer at model speed. deadline.ts:15 ↗


Long agent conversations are managed explicitly
The minter separates reusable static instructions from per-job context for provider caching. It begins background compaction at a 250,000-token input threshold and applies a higher 260,000-token guard while compaction is pending, with provider-side compaction as a backstop. Skill-read notes help the model rediscover guidance dropped from its immediate context. The outcome reviewer retains access to archived history instead of pretending a compacted conversation is complete evidence. These are engineering choices visible in the source; this report does not measure their cost savings. idle-compaction.ts:9 ↗ openai.ts:145 ↗ outcome-review.ts:319 ↗

15 / ENGINEERING JUDGMENT
What is compelling—and what deserves care.


The strongest ideas
Moving reasoning out of repeated execution is a coherent architecture for stable, recurring tasks. The generated source is inspectable and editable, and the runtime contract can be served through MCP without a new model plan. Separating proposed action from observed outcome is especially valuable for writes. Finally, the boundary between shared core and local host is explicit enough to audit: you can identify which hooks are composed instead of inferring capabilities from names in the tree. These are architectural judgments grounded in the traced paths. pomerado.ts:19 ↗ run-operation.ts:75 ↗ outcome-review.ts:319 ↗ hosted-features.ts:15 ↗


The main engineering costs
The state space is large. Input questions, login recipes, site navigation, writes, lost responses, browser lifecycle, source changes, and publication reviews interact. The minter harness itself is thousands of lines, with a substantial contract surface. The extensive tests help, but they cannot eliminate ambiguity in an external website. Inference: focused behavioral tests and careful evidence propagation are more important here than reducing every path to a generic success/error wrapper. harness.ts:969 ↗ contracts.ts:843 ↗ standalone-uncertain-commit.spec.ts:99 ↗


Generated browser integrations remain coupled to site behavior. A label change can be recoverable; a different login journey, changed semantics, or new bot protection may require rebuilding. The local host has no automatic maintenance service. It is therefore most attractive when a task repeats often enough to justify creation and validation, the site is reachable from the intended environment, and the result can be checked. This is a suitability judgment, not a measured reliability claim. hosted-features.ts:15 ↗ run-operation.ts:75 ↗


Things I would not infer from a successful mint
  • That all declared inputs were thoroughly tested, particularly for signed-in reads or writes.
  • That Guardian establishes a hard OS isolation boundary or a formal proof of harmlessness.
  • That an integration remains reviewed after editing its code or deployment configuration.
  • That cancellation or an error response means the website did not change.
  • That the full hosted product is implemented by the local CLI.
  • That the saved directory is portable without its runtime, browser, and corrected local paths.


Those limits do not invalidate the approach. They tell you where to spend validation effort and how to integrate the tool responsibly into a larger agent system.

17 / KEEP THIS MAP HANDY
A short glossary and a useful reading order.


Mint / artifact / publication
Mint: build an integration from a website task. Artifact: retained source plus machine-readable operation contracts. Publication: acceptance and saving of that integration; it does not inherently upload it anywhere.


Authority / purpose / target
Authority: the requested read/write scope and accepted owner instructions. Purpose: why a submitted step is running—explore, authenticate, example, test, or act. Target: the execution environment. The shared schema names targets that a particular host may refuse.


Guardian / outcome reviewer / runtime
Guardian: reviews proposed work while minting. Outcome reviewer: assesses evidence of writes after execution. Runtime: executes the retained operation without a new model review on every call.


Commit mark / verification / idempotency key
Commit mark: evidence that execution is entering a named state-changing step. Verification: recorded confirmation or readback supporting an outcome. Idempotency key: identity that prevents the host from treating a repeated submission as a new job within its retention scope.
